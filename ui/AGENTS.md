# GlassEgo UI 目录工作指南

## 适用范围与优先级

- 本文件适用于其所在目录及所有子目录。
- 本文件与上级目录的 `AGENTS.md` 共同生效；本文件负责补充 `ui/` 的具体要求。
- 系统指令、开发者指令和用户当前请求的优先级高于本文件。
- `ui/` 是 GlassEgo 的界面子目录。处理 UI 任务时，默认只修改本目录；需要调整其他目录时，必须由用户明确授权。

## 核心原则

- **简洁优先**：每次变更尽量简单，只影响最少的代码。
- **绝不偷懒**：定位并解决根因，不使用临时修复，坚持资深开发者标准。
- **最小影响**：只修改必要部分，避免引入新的缺陷。

## UI 职责与边界

- `ui/` 用于未来基于 PyQt 或其他兼容 Qt 框架的数据采集、数据单元管理和预处理结果可视化；当前尚无可运行的界面实现，不要把规划内容描述成已有能力。
- UI 只负责界面展示、用户交互、任务编排和状态反馈。手部检测、HaMeR 推理、轨迹优化、坐标计算等算法必须调用 `preprocess/` 的稳定接口，不得在 UI 中复制实现。
- 设备接入和原始传感器采集逻辑属于 `datacollection/`；UI 只能通过明确接口启动、停止和监控采集任务，不得在窗口或控件类中实现设备协议。
- 数据单元遵循 `data/<unit>/` 布局。原始视频、IMU、姿态和标定文件默认只读；删除、覆盖或移动原始数据必须由用户明确触发并经过确认。
- UI 不得自行维护另一套手部关节索引、坐标系、时间戳单位或序列化格式。显示和管理数据时应复用 `preprocess/data_types/` 的共享契约。
- 视频解码、模型推理、批量扫描和文件导出等耗时任务不得运行在 Qt 主线程中；应使用 Qt 的线程或任务机制，并向界面报告进度、错误和取消状态。
- 不在界面代码中硬编码绝对路径、设备专属路径、模型地址或凭据。路径、设备和运行选项通过显式配置或调用参数传入。
- 新增 PyQt、Qt binding 或其他 UI 依赖时，必须同步检查仓库级依赖和安装入口，不在 `ui/` 中复制一套独立安装流程。
- 不提交 UI 运行产生的缓存、日志、临时文件、视频、模型权重和其他生成产物。UI 专属资源、配置和测试应放在 `ui/` 内，并遵循仓库的 Git 忽略规则。
- 需要展示图像或视频时，必须明确 RGB/BGR 转换边界、图像尺寸和时间戳单位，不得在 UI 层改变底层数据语义。

## 工作流

### 1. 默认使用计划节点

- 任何非琐碎任务，包括 3 步以上的任务或架构决策，都必须先制定并维护计划。
- 验证步骤也必须纳入计划，而不仅用于实现阶段。
- 提前写清规格、成功标准和验证检查点，减少歧义。
- 一旦实际情况偏离计划，立即停止并重新规划，不要继续硬推。

多步骤任务使用以下格式：

```text
1. [步骤] -> 验证：[检查点]
2. [步骤] -> 验证：[检查点]
3. [步骤] -> 验证：[检查点]
```

### 2. 子代理策略

- 大量使用子代理，保持主上下文窗口整洁。
- 将研究、探索和可并行分析交给子代理处理。
- 复杂问题应通过子代理投入更多算力。
- 每个子代理只负责一个明确方向。

### 3. 先思考，再编码

- 不要假设，也不要隐藏困惑；明确说明假设、疑问和取舍。
- 实现前若存在不确定项，先询问用户。
- 如果存在多种解释，全部列出，不要默默选择。
- 如果存在更简单的方法，应主动说明；有充分理由时提出反对意见。
- 如果需求不清楚，停止实现，指出具体歧义并提问。

### 4. 目标驱动执行

- 开始前定义成功标准，并持续执行到验证通过。
- 将任务转化为可验证目标，例如：
  - “增加验证” -> 先为无效输入编写测试，再让测试通过。
  - “修复 bug” -> 先编写能够复现问题的测试，再让测试通过。
  - “重构 X” -> 确保重构前后的测试都通过。

## 实现规范

### 1. 简单优先

- 用最少的代码解决问题，不编写投机性代码。
- 不实现需求范围之外的功能。
- 不为一次性使用的代码创建抽象。
- 不添加未被要求的灵活性或可配置性。
- 不为不可能发生的场景编写错误处理。
- 如果 200 行代码可以缩减到 50 行，应重写为更简单的实现。
- 随时检查：资深工程师是否会认为当前实现过于复杂？如果是，就简化。

### 2. 手术式修改

- 只修改完成当前任务所必需的部分，只清理自己造成的问题。
- 编辑现有代码时：
  - 不要顺便改进相邻代码、注释或格式。
  - 不要重构没有问题的代码。
  - 匹配现有代码风格，即使你个人偏好不同。
  - 可以报告无关的死代码，但不要擅自删除。
- 当本次变更产生未使用项时：
  - 删除因本次变更而未使用的导入、变量和函数。
  - 除非用户明确要求，否则不要删除此前已经存在的死代码。
- 每一行修改都必须能够直接追溯到用户请求。

### 3. 要求优雅，但保持平衡

- 非琐碎改动前暂停确认：是否存在更优雅的方案？
- 如果实现显得临时或拼凑，应基于当前掌握的信息重新设计。
- 简单问题不要过度工程化。
- 每次提交结果前，重新审视实现是否足够简单、清晰和可靠。

### 4. 代码风格与复用

- 优先遵循用户和仓库现有的代码风格。
- 尽量保持模块化、高内聚和低耦合。
- 如果现有风格存在明显问题，应及时说明并给出修改建议。
- 优先复用成熟开源方案和仓库已有能力，不重复造轮子。

## 验证与测试

- 验证范围应与改动风险相匹配，并纳入任务计划。
- 未修改且已确认正确的代码不需要额外测试，以减轻工作流程。
- 如果需要编写临时测试代码，将其放在仓库对应目录下，并确保 Git 不跟踪这些测试文件，避免污染仓库。
- 完成前确认实现、验证结果和已知限制都已明确说明。
